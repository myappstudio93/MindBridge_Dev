Architecture Principles

Four constraints from the PRD that shape every box in the diagram below — not general best practice, but the specific reasons this system is arranged the way it is.

01 — Trust boundary

AI is never the terminal node. Every AI-touched path (chat, voice, brief generation) ends at a human — a therapist, an iCall counsellor, or a peer moderator. This is why the AI/ML layer sits between services and data, never facing the user directly.

02 — Crisis latency

<5s crisis detection can't share a queue with 1.5s p95 chat. Crisis Detection is a decoupled service with its own priority lane, not a feature bolted onto Chat Service — see the critical path section below.

03 — Data minimisation

Sensitive data is stored only as long as it's useful. Voice audio is processed and deleted within 60 seconds; it never reaches long-term storage. This shrinks the blast radius of the single highest-severity risk in the PRD (R2).

04 — No re-platforming

0 → 100K DAU is an explicit NFR, not an aspiration. Every service is stateless and independently scaled from day one — the cost is more ops surface for a pre-PMF team than a monolith would carry.

This path is exempt from standard request queuing: it interrupts the primary chat response rather than waiting behind it. Conservative thresholds are intentional — the PRD accepts false positives (an unnecessary CTA shown) to avoid false negatives (a missed signal).

Cross-Cutting Concerns

These don't live in one layer — they're enforced across all of them.

Security & Compliance

  • AES-256 at rest, TLS 1.3 in transit, all layers
  • End-to-end encryption on therapy video sessions
  • Data residency locked to AWS Mumbai (DPDP)
  • Per-service least-privilege IAM; no shared credentials

Scaling

  • HPA on CPU/memory for steady-state services
  • KEDA for event-driven load (chat bursts, circle activity)
  • Read replicas isolate analytics queries from transactional load
  • CDN-first content delivery for sub-100ms Tier 2 load times

Observability

  • Datadog APM across every service, correlated by trace ID
  • Sentry for client + server error capture
  • PagerDuty on-call, <5min mean time to detect
  • Crisis Detection has its own dedicated alert channel

Open Questions for Engineering Review

Gaps the PRD leaves to architecture and engineering to close before Sprint 1.

01

LLM routing policy is undefined. Is Claude primary with GPT-4o as fallback, or per-request routing by cost/latency? The LLM Gateway can't be built until this is decided.

02

Video SDK choice is asserted, not validated. Agora is named throughout, but there's no documented cost/latency comparison against Twilio or 100ms — worth a short spike given it's a per-minute cost driver at scale.

03

Crisis NLP model is unspecified. "Keyword + sentiment" needs a named model, a threshold-tuning plan, and a red-team dataset before this can be a Month 0 launch gate.

04

Kafka may be premature at MVP scale. Worth confirming the DAU forecast justifies the operational overhead now, versus batch-loading Redshift directly until Phase 2 volume arrives.

05

No documented DR strategy. Single-region (Mumbai) is fine for launch, but a health-data platform needs a stated RTO/RPO and backup-region plan before Series A diligence.
